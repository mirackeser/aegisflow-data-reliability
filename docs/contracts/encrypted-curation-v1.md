# Encrypted signed curation v1

The optional `curation` profile provides `retain_encrypted_curation` and `read_encrypted_curation` in `benchmark.encrypted_curation_store`. They accept the same signed evidence/current policy parameters as signed retention, plus a host-supplied exact 32-byte `key` and opaque `key_id`. No key is generated, discovered, logged or persisted by these APIs. The host must authorize and select the key externally; a stored key ID grants no authority.

Before creating any file, the writer validates sources and signatures and prepares all signed artifacts in memory. Each of the seven artifacts and the inner signed header is encrypted with AES-256-GCM, a fresh OS-random 12-byte nonce and a full 16-byte authentication tag. Associated data binds the domain/version, public key ID, random 128-bit snapshot ID and artifact name. Stored blobs are nonce followed by ciphertext/tag. The closed [outer header](encrypted-curation-header-v1.json) exposes only format, key ID, random snapshot ID and ciphertext hashes. Its digest must be retained independently by the trusted host.

Both formats share the exclusive mode-0600 transactional SQLite writer and bounded physical-table reader. This format contains exactly nine rows. Sources, labels, signatures, public grants and inner plaintext hashes never enter SQLite, journals or temporary plaintext files through this API. Ciphertext size permits the existing one-million-byte plaintext limit plus 28 bytes of encryption overhead; SQLite row/resource limits remain in force. Length, count and public metadata still leak. Reads authenticate/decrypt all artifacts in memory, recompute signed evidence integrity and require current external grants, revision and clock before returning labels. Wrong key, changed associated data, malformed headers, ciphertext substitution and expired/revoked policy fail closed. Disagreement still exports no labels. Plaintext formats cannot be cross-read and are never implicitly migrated.

## Key and access boundary

The trusted host owns secret delivery, authorization, backup/recovery, rotation and a conservative per-key encryption-use limit. Random nonces have a probabilistic collision bound; this module is not a global nonce allocator or distributed key-usage ledger. Use dedicated dataset/tenant keys, rotate before one million artifact encryptions per key, and do not share these keys with other applications. This is a host operational prerequisite, not an enforced counter. Rotation requires explicit new-file re-retention under an approved key; no in-place rewrite or key retirement API exists. Do not pass real enterprise data until managed key delivery and curator/evaluator access separation are implemented.

Possession of an encryption key permits decryption and is not independent organizational identity. Runtime memory, process compromise and privileged host access remain outside at-rest protection. Python does not guarantee key/plaintext zeroization. Existing plaintext snapshots remain plaintext; operators must govern them separately. No production KMS, SSO, sealed-holdout approval or live model acceptance is introduced.

The pinned library's [AESGCM documentation](https://cryptography.io/en/stable/hazmat/primitives/aead/#cryptography.hazmat.primitives.ciphers.aead.AESGCM) defines nonce uniqueness, associated data and invalid-tag behavior. Tests use ephemeral memory-only keys and real encrypted SQLite snapshots.
