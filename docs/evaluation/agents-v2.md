# Agent runtime evaluation (v2)

Generated by `python -m aegisflow_dr.agents.agents_eval --protocol 2` by replaying `fixtures/evaluations/agents-llm-recording-v2.json` (development, validation and held-out (`--include-heldout`)).

**Scope.** The 36-role agent runtime on simulated incident cases with a local 4B model (qwen3:4b) that is advisory and Judge-gated; A23 reads a deterministic qualitative reading of each observation (prompt version 3). Simulated scenarios on generated series only: no real incidents, no root cause, no production connection, no autonomous remediation.

**What changed in v2.** A23 no longer receives the catalog list. Each observation carries a qualitative reading computed deterministically from aggregates (`aegisflow_dr.readings`: a mean scaled by a power of ten, shifted or unchanged; a wider, narrower or unchanged spread; rows that dropped or increased; late data; more empty values in one contiguous run or scattered), and the prompt states each mechanism's signature in those words and asks for a ranking (prompt version 3). The readings use the same aggregates and documented thresholds the probes use, so agreement now measures whether the model maps documented signatures to readings, not independent diagnosis. The prompt was written and tried on v1 development groups only and frozen before this corpus was recorded (docs/superpowers/specs/2026-11-28-a23-readings-design.md). The v1 report (`agents.md`, prompt version 2) stays as committed.

## Corpus

40 groups (groups 160-199) from the baseline evaluation's generator, with the fourteen scenario injections of the hypothesis loop evaluation (`hypotheses_eval.scenario`, imported, not copied). The corpus is disjoint from the baseline comparison evaluation (D05c, groups 0-59) and the hypothesis loop evaluation (F04, groups 60-119) and the v1 agents evaluation (groups 120-159): the generator is seeded by the group number, so no group, base series or payload is shared with them.

Groups are split by a hash of the group number (salt `aegisflow-agents-eval-v2`, buckets 6/2/2 out of 10), realized as development 26, validation 5 and held-out 9 groups; all scenarios of a group stay in one split. Held-out is small, so its intervals are wide: a perfect 9/9 has a Wilson 95% lower bound of 70.1%.

Each case is one `run_case`: the baseline built from the group's 3 reference batches, the scenario's current batch and `as_of`; no second file, no retriever and no run history. Transports are in process (no MCP or A2A hop), no context cache is used, and the budgets are the catalog defaults (8 specialists, 12 model calls, 40,000 tokens, 90 s).

## Model and recording

Model `qwen3:4b` through Ollama on 127.0.0.1 (temperature 0, seed 7, thinking off, output constrained to each role's JSON Schema), prompt version 3, recorded on 2026-11-28: 1600 model calls over 560 live runs. The report replays the recording by the SHA-256 of each exact request; a request that was not recorded is MODEL_UNAVAILABLE, never a guess. Latencies are the live ones from the recording; the replay clock advances by them, so budgets and deadlines see the live timing.

Definitions. *Exact set*: the selected specialists (A07-A22) equal the expected set. *Precision* and *recall* pool every specialist decision of the split. *Schema-valid JSON*: calls whose reply parsed and validated, over calls that returned a reply (TIMEOUT and MODEL_UNAVAILABLE are counted separately). *Judge kept as advisory*: the role's model-based claims the Judge labelled advisory, over those it labelled advisory or rejected (model output is never accepted as a finding). *A23 top-1*: the first mechanism A23 lists is the injected one; *A23 any*: the injected mechanism is among its at most three; both over every case of a modelled scenario (no suggestion counts as no agreement); *mechanisms listed* tallies how many mechanisms each completed A23 suggestion named (a longer list makes *any* easier); *catalog-order echo*: among non-empty suggestions, the list equals the first catalog mechanisms that explain any of the case's observations, in catalog order (the model repeating the prompt's order rather than discriminating; this column and the repeated-mechanism count were added after a development and validation report had been rendered, and before held-out was scored). *Loop sole-supported*: the deterministic loop (`hypotheses.investigate`, as run by A24) supports exactly the injected mechanism and no other (mechanism level, columns ignored). For `clean` and the unmodelled scenarios, *misattributed* means a catalog mechanism other than `genuine_change` was suggested (A23) or supported (loop). Rates are `count/total = percent [95% Wilson interval]`; `n/a` means nothing to measure or the metric does not apply.

## Reading these numbers

- The model is a local 4B model (`qwen3:4b`, 4-bit quantised) used as an advisor. Its output is never evidence: the Judge labels model-based claims advisory at best, and only specialist claims can be accepted as findings. No result here is a root cause.
- Agreement of A23 with an injected label on simulated scenarios is not diagnostic accuracy on real data. The scenarios, the readings and their thresholds, the signatures in the prompt and the probes were written by the same authors from the same catalog, so agreement measures whether the model maps documented signatures to deterministic readings. A reading that fits two mechanisms equally cannot be told apart.
- A23's prompt asks for the candidates from the best fit to the worst, so *top-1* is the model's first choice. *Catalog-order echo* stays as a check that the list does not simply follow the catalog; for a list of one mechanism it is true whenever that mechanism is the first in catalog order that explains the observations, so it reads 100% on unit change, sampling change, delivery delay and field outage by construction.
- On duplicate delivery the model pads its list with `partial_load` and `sampling_config_change` and claims they explain the volume increase, which neither does; the Judge rejects those claims (`mechanism_does_not_explain`), so the A23 advisory rate is below 100% while its first choice is unaffected. This was seen on development after the prompt had been frozen and was not tuned away.
- The deterministic loop and A23 answer different questions: the loop tests mechanisms with fixed probes, A23 only proposes. The side-by-side columns show both on the same cases, not a contest between equals.
- Role selection is deterministic code implementing the role table, and the expected sets come from the same table, so precision and recall test the implementation on these cases (internal consistency), not whether the table picks the right experts for real incidents. All scenarios share the same case inputs, so the expected set is the same everywhere; a difference can only come from observation-driven triggers (A17).
- Pooled precision and recall treat each role decision as independent; decisions within one case are correlated, so their intervals are optimistic. *Exact set* (one trial per case) is the conservative reading. Scenarios of one group share one baseline, so rates across scenarios are not independent.
- Schema-valid JSON is measured under constrained decoding (Ollama's `format` with each role's schema), so it reflects the decoder plus the model, not the model's unaided formatting.
- A22 and A30 make no model call on this corpus (no retriever or history; not an order extract), so their model behaviour is not measured here.
- Latencies are one sequential live run on this machine with one model instance and no context cache; they vary with hardware and load. Run wall times include the in-process rule agents and are not the default `auto` transport (no MCP or mutual-TLS A2A hop).
- Temperature 0 and a fixed seed do not guarantee identical output across Ollama versions or hardware; the recording fixes one live run, and the replay-fidelity line shows whether replay reproduces it.
