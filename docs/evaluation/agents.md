# Agent runtime evaluation

Generated by `python -m aegisflow_dr.agents.agents_eval` by replaying `fixtures/evaluations/agents-llm-recording-v1.json` (development, validation and held-out (`--include-heldout`)).

**Scope.** The 36-role agent runtime on simulated incident cases with a local 4B model (qwen3:4b) that is advisory and Judge-gated. Simulated scenarios on generated series only: no real incidents, no root cause, no production connection, no autonomous remediation.

## Corpus

40 groups (groups 120-159) from the baseline evaluation's generator, with the fourteen scenario injections of the hypothesis loop evaluation (`hypotheses_eval.scenario`, imported, not copied). The corpus is disjoint from the baseline comparison evaluation (D05c, groups 0-59) and the hypothesis loop evaluation (F04, groups 60-119): the generator is seeded by the group number, so no group, base series or payload is shared with them.

Groups are split by a hash of the group number (salt `aegisflow-agents-eval-v1`, buckets 6/2/2 out of 10), realized as development 21, validation 9 and held-out 10 groups; all scenarios of a group stay in one split. Held-out is small, so its intervals are wide: a perfect 10/10 has a Wilson 95% lower bound of 72.2%.

Each case is one `run_case`: the baseline built from the group's 3 reference batches, the scenario's current batch and `as_of`; no second file, no retriever and no run history. Transports are in process (no MCP or A2A hop), no context cache is used, and the budgets are the catalog defaults (8 specialists, 12 model calls, 40,000 tokens, 90 s).

## Model and recording

Model `qwen3:4b` through Ollama on 127.0.0.1 (temperature 0, seed 7, thinking off, output constrained to each role's JSON Schema), prompt version 2, recorded on 2026-11-25: 1600 model calls over 560 live runs. The report replays the recording by the SHA-256 of each exact request; a request that was not recorded is MODEL_UNAVAILABLE, never a guess. Latencies are the live ones from the recording; the replay clock advances by them, so budgets and deadlines see the live timing.

Definitions. *Exact set*: the selected specialists (A07-A22) equal the expected set. *Precision* and *recall* pool every specialist decision of the split. *Schema-valid JSON*: calls whose reply parsed and validated, over calls that returned a reply (TIMEOUT and MODEL_UNAVAILABLE are counted separately). *Judge kept as advisory*: the role's model-based claims the Judge labelled advisory, over those it labelled advisory or rejected (model output is never accepted as a finding). *A23 top-1*: the first mechanism A23 lists is the injected one; *A23 any*: the injected mechanism is among its at most three; both over every case of a modelled scenario (no suggestion counts as no agreement); *mechanisms listed* tallies how many mechanisms each completed A23 suggestion named (a longer list makes *any* easier); *catalog-order echo*: among non-empty suggestions, the list equals the first catalog mechanisms that explain any of the case's observations, in catalog order (the model repeating the prompt's order rather than discriminating; this column and the repeated-mechanism count were added after a development and validation report had been rendered, and before held-out was scored). *Loop sole-supported*: the deterministic loop (`hypotheses.investigate`, as run by A24) supports exactly the injected mechanism and no other (mechanism level, columns ignored). For `clean` and the unmodelled scenarios, *misattributed* means a catalog mechanism other than `genuine_change` was suggested (A23) or supported (loop). Rates are `count/total = percent [95% Wilson interval]`; `n/a` means nothing to measure or the metric does not apply.

## Reading these numbers

- The model is a local 4B model (`qwen3:4b`, 4-bit quantised) used as an advisor. Its output is never evidence: the Judge labels model-based claims advisory at best, and only specialist claims can be accepted as findings. No result here is a root cause.
- Agreement of A23 with an injected label on simulated scenarios is not diagnostic accuracy on real data. The scenarios, the mechanism catalog (with the checks each mechanism explains, which A23 sees in its prompt) and the prompts were written by the same authors, so agreement measures whether the model maps observation checks to catalog mechanisms the way the catalog intends.
- A23's prompt does not ask for a ranking, so *top-1* is the first mechanism the model happened to list, not a calibrated best guess; *any* is the fairer reading of a list of up to three.
- The deterministic loop and A23 answer different questions: the loop tests mechanisms with fixed probes, A23 only proposes. The side-by-side columns show both on the same cases, not a contest between equals.
- Role selection is deterministic code implementing the role table, and the expected sets come from the same table, so precision and recall test the implementation on these cases (internal consistency), not whether the table picks the right experts for real incidents. All scenarios share the same case inputs, so the expected set is the same everywhere; a difference can only come from observation-driven triggers (A17).
- Pooled precision and recall treat each role decision as independent; decisions within one case are correlated, so their intervals are optimistic. *Exact set* (one trial per case) is the conservative reading. Scenarios of one group share one baseline, so rates across scenarios are not independent.
- Schema-valid JSON is measured under constrained decoding (Ollama's `format` with each role's schema), so it reflects the decoder plus the model, not the model's unaided formatting.
- A22 and A30 make no model call on this corpus (no retriever or history; not an order extract), so their model behaviour is not measured here.
- Latencies are one sequential live run on this machine with one model instance and no context cache; they vary with hardware and load. Run wall times include the in-process rule agents and are not the default `auto` transport (no MCP or mutual-TLS A2A hop).
- Temperature 0 and a fixed seed do not guarantee identical output across Ollama versions or hardware; the recording fixes one live run, and the replay-fidelity line shows whether replay reproduces it.
- Prompts (version 2) were fixed before development was scored and were not changed after looking at validation; held-out is scored once, and anything it reveals is reported as a weakness.
